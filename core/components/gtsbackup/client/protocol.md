# Протокол gtsBackup (версия 1)

Обмен между клиентом и сайтом с пакетом gtsBackup. Документ лежит рядом с клиентом из комплекта —
в папке `core/components/gtsbackup/client/` (`gtsbackup.php`, запуск в Windows — `gtsbackup.cmd`).
По нему можно написать и свой клиент на любом языке: всё, что нужно, — HTTP POST и чтение tar.gz.

## Эндпоинт и авторизация

```
POST https://<сайт>/assets/components/gtsbackup/action.php
X-Gtsbackup-Token: gbk_…
Content-Type: application/x-www-form-urlencoded | multipart/form-data
action=<действие>&…
```

- Токен создаёт администратор: «Компоненты → Бекапы → Токены → Создать токен». Он бессрочный,
  право у него одно — снять бекап этого сайта. В базе хранится только sha256, сам токен показывается
  один раз. Отозвать — снять галочку «Активен» или удалить строку.
- Токен можно передать и как `Authorization: Bearer gbk_…` или полем POST `token`. В GET — нельзя
  (попадёт в логи веб-сервера).
- HTTP и HTTPS работают оба. `gtsbackup_require_https = 1` запрещает HTTP; `gtsbackup_ip_whitelist`
  ограничивает адреса клиентов.
- Ответы JSON: `{"success": 1|0, "message": "…", "data": {…}}`. Потоковые действия (`download`, `db`)
  отдают файл. Коды: `400` — неверный запрос, `403` — токен, HTTPS, IP или пакет выключен, `404` —
  задания нет, `409` — состояние не то (см. `message` и `data.code`), `416` — Range за концом файла.

## Действия

| action | Параметры | Ответ |
|---|---|---|
| `ping` | — | `protocol`, `version`, `site_name`, `http_host`, `token` (имя), `php`, `sources`, `step_time`, `db_method`, `https` |
| `create` | `mode=full\|diff`; для diff — `base_job` или файл `base` | `job`, `files_total`, `bytes_total`, `files_site`, `deleted`, `warnings`, `step_time` |
| `step` | `job` | `done`, `files_done/total`, `bytes_done/total`, `archive_size`, `warnings`, `step_warnings[]` |
| `download` | `job`, `what=files\|manifest` | файл; `Range: bytes=N-` — докачка (`206`), заголовок `X-Gtsbackup-Size` — полный размер |
| `finish` | `job` | задание закрыто, журнал записан, папка на сервере удалена |
| `cancel` | `job` | то же без сохранения манифеста |
| `db` | — | поток `sql.gz`, заголовок `X-Gtsbackup-Db-Method: mysqldump\|php` |

Задание видно только тому токену, который его создал.

## Файлы: порядок обмена

```
create(mode)  →  step … step (пока done = false)  →  download manifest  →  download files  →  finish
```

1. **create** обходит дерево сайта и сразу пишет на сервере два файла задания:
   - `manifest.jsonl.gz` — все файлы сайта на этот момент;
   - список того, что пойдёт в архив: всё при `full`, изменённое и новое при `diff`.

   Обход занимает секунды даже на десятках тысяч файлов, архива ещё нет.
2. **step** дописывает архив столько секунд, сколько задано в `gtsbackup_step_time` (по умолчанию 20).
   Так ни один запрос не упирается в таймаут nginx или php-fpm, и сайт с гигабайтами файлов
   собирается за любое число шагов. Повтор `step` после обрыва безопасен. Параллельный шаг того же
   задания получит `409`.
3. **download** — сначала манифест, потом архив. Архив отдаётся только после `done = true`. Если связь
   оборвалась, клиент продолжает с того же места через `Range`.
4. **finish** закрывает задание. У полного бекапа сервер сохраняет манифест
   (`core/packages/_gtsbackup/manifests/`, по 3 последних на токен): это база для следующих
   дифференциальных. Брошенные задания удаляются через `gtsbackup_job_ttl_hours`.

### Дифференциальный бекап

Дифференциальный бекап всегда считается от **полного**, а не от предыдущего дифференциального.
Поэтому для восстановления нужны ровно два архива: полный и выбранный дифференциальный.

- Клиент шлёт `base_job` — `job` полного бекапа. Если сервер этот манифест уже не помнит, он отвечает
  `409` с `data.code = "base_missing"`. Тогда клиент повторяет `create` с файлом `base`
  (`manifest.jsonl.gz` полного бекапа, multipart).
- Файл считается изменённым, если у него другой размер или другое время изменения (mtime), либо его
  не было в базе.
- Файлы, которые были в базе, но пропали с сайта, перечислены в `meta.deleted` манифеста.

### Формат архива `files.tar.gz`

- Обычный tar (GNU): `tar -xzf`, Windows `tar.exe`, 7-Zip.
  - Имена длиннее 99 байт пишутся через `././@LongLink` (тип `L`).
  - Файлы больше 8 ГБ — размер в base-256.
  - Пустые папки — записи типа `5` (путь с `/` на конце).
- Каждый шаг пишет отдельный член gzip. Склейка членов — валидный gzip, и tar внутри идёт одним
  потоком: большой файл может начаться в одном шаге и закончиться в другом.
- Пути в архиве идут от корня бекапа (`gtsbackup_root`, по умолчанию корень сайта). Если `core` лежит
  вне корня, он попадает в архив под префиксом `@core/`.
- Если файл изменился между заголовком и чтением, архив остаётся целым: недостающее добивается
  нулями, лишнее обрезается. Такой файл попадает в `step_warnings`, а следующий бекап снимет его заново.

### Формат манифеста `manifest.jsonl.gz`

Строки JSON (gzip):

```
["assets/components/x/main.js", 1234, 1731400000]     путь, размер, mtime
["core/cache/", 0, 0]                                   пустая папка
{"meta": {"gtsbackup":1, "job":"…", "mode":"diff", "base_job":"…", "created":"…", "site":"…",
          "sources":["","@core/"], "files_total":9113, "files_in_archive":3, "bytes_in_archive":453,
          "deleted":["assets/old.txt"], "warnings":[…]}}
```

## База

`db` отдаёт дамп всей базы сайта одним потоком gzip. Сервер ничего не хранит, поэтому дамп всегда
полный (дифференциального у базы нет).

- `gtsbackup_db_method`:
  - `auto` — mysqldump, если он запускается, иначе выгрузка средствами PHP (для хостинга без mysqldump);
  - `mysqldump`, `php` — принудительно.
- mysqldump запускается с `--single-transaction --quick --hex-blob`. Пароль и список исключений
  передаются во временном файле опций, а не в командной строке.
- PHP-выгрузка:
  - снимок `START TRANSACTION WITH CONSISTENT SNAPSHOT`;
  - бинарные поля пишутся как `0x…`;
  - снимаются таблицы и представления; триггеры и процедуры — нет.
- `gtsbackup_db_nodata_tables` — у этих таблиц берётся только структура (по умолчанию `session`).
- `gtsbackup_db_ignore_tables` — эти таблицы не берутся совсем.
- В обоих списках имена пишутся без префикса.
- **Последняя строка дампа** — `-- gtsBackup-end: ok` или `-- gtsBackup-end: error <текст>`. HTTP-ответ
  уже отправлен с кодом 200, поэтому ошибку посреди дампа видно только по этой строке. Без неё дамп
  считается оборванным.

## Как это делает клиент

- **Режим `auto`.** Полный бекап снимается в трёх случаях: полного ещё нет; он старше `full_every_days`;
  от него уже снято `max_diff` дифференциальных. В остальных случаях снимается дифференциальный.
- **Хранение — цепочками.** Какой дифференциальный от какого полного, видно по папкам:

  ```
  <dest>/<сайт>/
      20261112-033000/                  цепочка: имя = время полного
          full/                         полный бекап
          diff-20261113-033000/         дифференциальные этого полного
          diff-20261114-033000/
      db-only/20261115-120000/          «только база» (--no-files)
      gtsbackup.log
  ```

  В каждой папке бекапа лежат `files.tar.gz`, `manifest.jsonl.gz`, `db.sql.gz` и `info.json`. У
  дифференциального в `info.json` есть поле `base` — номер своего полного. Номер бекапа — время
  снятия, по нему работают `verify` и `restore`.

  Пока бекап собирается, папка называется `.part-<время>`. Брошенные `.part-…` удаляются при следующем
  запуске.
- **Проверка.** После скачивания клиент читает архив до конца: число записей tar должно совпасть с
  числом, которое записал сервер. У дампа он проверяет последнюю строку.
- **Ротация.** Хранятся `keep_full` последних цепочек «полный + его дифференциальные». Цепочки
  старше удаляются целиком, одной папкой. Бекапов «только база» хранится `keep_db_only`.
- **Восстановление (`restore`).** В пустую папку разворачивается полный бекап, поверх него —
  дифференциальный. Затем удаляются файлы из `meta.deleted`, и рядом кладётся `_db.sql.gz`. Базу
  заливают руками: `gunzip -c _db.sql.gz | mysql <база>`.
