# gtsBackup

Бекап сайта MODX на локальный компьютер. Сайт по токену собирает полный или дифференциальный архив
файлов (tar.gz) и отдаёт дамп базы. Клиент забирает бекапы по HTTP/HTTPS, проверяет их,
хранит и сам удаляет старые (ротация).

## Быстрый старт

1. Поставить пакет на сайт.
2. «Компоненты → Бекапы → Токены → Создать токен» (название — чей компьютер). В окне:
   - **команда** — главное, её копируют;
   - ссылка на zip клиента (действует час) — нужна, только если клиента на этом компьютере ещё нет;
   - сам токен (показывается один раз).
3. **Первый сайт на этом компьютере:** скачать zip по ссылке и распаковать, например в `C:\gtsBackup`.
   **Не первый:** клиент уже стоит — пропустить.
4. Обычная консоль (права администратора не нужны), в папке клиента — команда из окна как есть:

   ```bat
   gtsbackup.cmd add mysite https://example.com/assets/components/gtsbackup/action.php gbk_… --dest=D:\Backups --now
   ```

   Команда:
   - проверит связь и покажет, какая папка сайта бекапится;
   - запишет все настройки сайта в его блок `sites.mysite` в `gtsbackup.json`;
   - поставит задачу «gtsBackup» от текущего пользователя в 03:30 — **только если её ещё нет**.
     У второго сайта задача уже есть: она не трогается и бекапит все сайты из конфига.
     Время меняют отдельно: `gtsbackup.cmd task 04:00`;
   - снимет первый полный бекап (`--now`).
5. `gtsbackup.cmd list` — что снято и что будет дальше; `gtsbackup.cmd check` — нет ли пропусков.

### Задача Планировщика

Задача создаётся через XML, от текущего пользователя:
- **Триггеры:** каждый день в `task_time` и через 5 минут после входа в Windows.
- **Пропущенный запуск** (компьютер был выключен) выполняется при первой возможности.
- **Запуск без окна консоли:** Планировщик запускает `gtsbackup-task.vbs`, тот — `gtsbackup.cmd scheduled` скрыто.
- **`scheduled`** бекапит сайты, у которых удачный бекап старше `min_interval_hours` (20 ч). Поэтому запуск
  и по времени, и при входе не плодит лишних бекапов.

Управление: `gtsbackup.cmd task` (показать), `task 04:00` (сменить время), `task remove` (удалить).

### Если бекапы не делаются

После каждого запуска задача проверяет все сайты. Если у сайта нет удачного бекапа `alert_days` дней
(по умолчанию 2), поверх всех окон появляется окно «gtsBackup» со списком таких сайтов и датой
последнего удачного бекапа. Причина — в `<dest>\<сайт>\gtsbackup.log`.

Как показывается окно: клиент пишет текст в `gtsbackup-alert.txt`, а показывает его сам `wscript` из
задачи (`MsgBox`). Окна процессов из скрытой цепочки Windows не показывает.

- Вручную: `gtsbackup.cmd check` (код выхода 1 — есть пропуски или нет задачи), `check --popup` — окном.
- На сайте: «Бекапы → Токены», колонка «Последний удачный бекап» по каждому компьютеру.

### Какая папка сайта бекапится

Корень сайта MODX (`MODX_BASE_PATH` — где `index.php` и `config.core.php`). `core` вне корня добавляется
сам, в архиве — `@core/`. Другой корень — настройка `gtsbackup_root`, исключения — `gtsbackup_exclude`.
Фактические пути показывают `ping`, `add` и `list`.

## Что и сколько хранится

Хранение цепочками — по папкам видно, какой дифференциальный от какого полного:

```
D:\Backups\mysite\
    20261112-033000\                 цепочка (имя = время полного)
        full\                        полный: файлы + база
        diff-20261113-033000\        дифференциальные ЭТОГО полного: изменения с момента полного + база
    20261119-033000\
        full\
    db-only\…                        только база (--no-files)
    gtsbackup.log
```

Дифференциальный всегда считается от полного своей цепочки, поэтому восстановление — ровно два архива.
`list` показывает дерево цепочек, сколько хранится из скольких и что сделает следующий запуск.

`auto` решает сам: полный, если полного нет, ему `full_every_days` дней или от него уже `max_diff`
дифференциальных; иначе дифференциальный. По умолчанию при ежедневном запуске:

| Настройка клиента | По умолчанию | Итог |
|---|---|---|
| `full_every_days` | 7 | полный раз в неделю |
| `max_diff` | 6 | 6 дифференциальных между полными |
| `keep_full` | 4 | 4 цепочки ≈ 4 недели: 4 полных + до 24 дифференциальных |
| `keep_db_only` | 14 | бекапов «только база» |

Лишние цепочки удаляются целиком после каждого удачного бекапа.

## Где что лежит

| Путь в пакете | Что это |
|---|---|
| [`core/components/gtsbackup/client/`](core/components/gtsbackup/client/) | **клиент**: `gtsbackup.cmd` + `gtsbackup.ps1` (Windows, ничего ставить не нужно), `gtsbackup.php` (Linux/macOS), пример настроек `gtsbackup.example.json` и [`protocol.md`](core/components/gtsbackup/client/protocol.md) — **описание протокола** обмена с сайтом. Папку целиком копируют на компьютер для бекапов |
| [`core/components/gtsbackup/docs/readme.txt`](core/components/gtsbackup/docs/readme.txt) | краткая инструкция покупателю (показывается при установке) |
| `core/components/gtsbackup/model/` | сервис `gtsBackup` и схема таблиц `gtsbackup_tokens`, `gtsbackup_log` |
| `assets/components/gtsbackup/action.php` | эндпоинт, на который ходит клиент |
| `_build/configs/` | настройки, меню, таблицы gtsAPI, зависимость от gtsAPI |

Клиент вместе с протоколом лежит в `core`, поэтому попадает в transport-пакет и на сайте после
установки оказывается в `core/components/gtsbackup/client/`. Клиент через веб не выполняется: он работает только
из командной строки.

## Сборка

`npm install`, затем `npm run build` — пакет ставится на сайт из `.env` (`VITE_APP_HOST`,
`VITE_DEV_TOKEN`, можно положить в `../.env`). Токен сборки — `npm run get_token`.

## Сайт

1. «Компоненты → Бекапы → Токены → Создать токен», указать название (чей компьютер).
   Токен бессрочный, право у него одно — бекап. Он показывается один раз — скопировать.
   В том же окне — готовая команда `gtsbackup.cmd add …`.
2. Настройки — «Системные настройки», пространство `gtsbackup`:

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `enabled` | 1 | выключатель эндпоинта |
| `require_https` | 0 | пускать только по HTTPS |
| `ip_whitelist` | — | с каких IP пускать (через запятую) |
| `root` | корень сайта | что бекапить; core вне корня добавляется сам (`@core/`) |
| `exclude` | `core/cache/`, `core/packages/_gtsbackup/`, `.git/`, `node_modules/` | исключения: путь с `/` внутри — от корня, без — имя на любой глубине, `/` в конце — только папка |
| `max_file_mb` | 0 | пропускать файлы больше N МБ |
| `step_time` | 20 | архив на сервере собирается порциями: один запрос `step` упаковывает файлы в общий tar.gz столько секунд (тысячи файлов), клиент повторяет, пока не готово, затем качает архив целиком одним файлом. Должно быть меньше таймаута веб-сервера |
| `compress_level` | 6 | gzip 1–9 |
| `tmp_path` | `core/packages/_gtsbackup/` | где собирается архив до скачивания (нужно место) |
| `job_ttl_hours` | 24 | когда удалять брошенные задания |
| `db_method` | auto | `mysqldump` / `php` / `auto` |
| `mysqldump_bin` | — | путь к mysqldump; пусто — из PATH |
| `db_nodata_tables` | session | только структура |
| `db_ignore_tables` | — | не брать совсем |

Журнал бекапов — вкладка «Журнал» там же.

Если сайт закрыт белым списком на веб-сервере, нужно открыть путь `/assets/components/gtsbackup/action.php`.

## Компьютер с бекапами

**Windows 10 (1803+) / 11 — ставить ничего не нужно.** `gtsbackup.cmd` запускает `gtsbackup.ps1`
(PowerShell 5.1, `-ExecutionPolicy Bypass`). Клиент пользуется только встроенным:
- `curl.exe` — HTTP/HTTPS, докачка (`-C -`), загрузка манифеста. Токен передаётся через файл заголовков
  (`-H @файл`), а не в командной строке;
- `tar.exe` — проверка архива (`-tzf`) и восстановление (`-xzf`);
- задачу ставит `Register-ScheduledTask`.

HTTPS идёт через Schannel и хранилище сертификатов Windows. Если сеть не пускает к спискам отзыва
сертификатов, поставьте у сайта `"ssl_no_revoke": true`.

**Linux / macOS** — тот же клиент на PHP: `php gtsbackup.php …` (PHP 7.4+, curl, zlib), расписание — cron
(`php gtsbackup.php scheduled`). Оба клиента используют один формат `gtsbackup.json` и одну раскладку папок.

```bat
gtsbackup.cmd list                                  &rem цепочки, сколько хранится, что дальше
gtsbackup.cmd backup all                            &rem снять сейчас (auto)
gtsbackup.cmd backup mysite full                    &rem принудительно полный
gtsbackup.cmd verify mysite 20261113-033000         &rem номер = время бекапа (из list)
gtsbackup.cmd restore mysite 20261113-033000 D:\restore\mysite   &rem дифф.: сам возьмёт свой полный
gtsbackup.cmd task 03:30                            &rem поставить/поменять время задачи
schtasks /Run /TN gtsBackup                         &rem запустить задачу сейчас
```

Настройки — в `gtsbackup.json`, **у каждого сайта свои** (блок `sites.<имя>`). `add` записывает туда
все значения явно, их можно задать сразу: `--keep-full=8 --max-diff=6 --alert-days=3`. Общее — только
`task_time` (время задачи). Пример — [`gtsbackup.example.json`](core/components/gtsbackup/client/gtsbackup.example.json).

- `url`, `token`, `dest` — сайт, его токен, куда класть бекапы;
- `keep_full`, `max_diff`, `full_every_days`, `keep_db_only` — см. «Что и сколько хранится»;
- `alert_days` — через сколько дней без удачного бекапа показывать окно (0 — не показывать);
- `min_interval_hours` — плановый запуск пропускает сайт, если удачный бекап свежее;
- `files` / `db` — что снимать;
- `insecure` — самоподписанный сертификат;
- `cacert` — путь к `cacert.pem`, если в php.ini не задан `curl.cainfo` (частая ошибка HTTPS на Windows).

`gtsbackup.json` содержит токены — в git его не класть (есть в `.gitignore`).

Код выхода: 0 — успех, 1 — ошибка. Лог: `<dest>\<сайт>\gtsbackup.log`.
